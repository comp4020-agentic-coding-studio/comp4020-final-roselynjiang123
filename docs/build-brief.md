## 1. Product in one paragraph

A two-person, real-time, persistent teaching game for nursing students: **paired medication-check practice on a simulated adult ward**. Two students each check the same six fictional medication tasks on their own, sign, then see together what each of them found, what both missed, and why. A short training summary, three new transfer situations and an end review follow. A session takes about 20–25 minutes. It is not a clinical tool, not a competence assessment and not evidence that double checking works.

Working definition of good (the README argument is the student's; the rules below must stay consistent with it):
1. Protect independent judgement: before both sign, nobody can see the partner's answer, the reference answer or any feedback.
2. Make "who found what" visible: separate agreement, accuracy, complementary finds and shared misses.
3. Turn findings into a next step with evidence, and keep "the records match" apart from "this dose should be given now".
4. Be honest about content and effect: every case shows its version, sources and real review status; nothing claims clinical effect.

## 2. Out of scope (do not build)

Live or runtime AI of any kind; accounts or login; teacher dashboard; chat or free-text answers; leaderboards; timers or speed scores; badges; random or generated cases; drug encyclopedia; walking ward map, health bars or "patient dies" mechanics; pixel fonts for body text; post-reveal resubmission; spectator mode; replacing absent players; non-independent mode or A/B experiments; cross-session "you keep making this error" inference (see §8.4 for the descriptive history that replaces it); PDF generation service (browser print only); new infrastructure (Redis, WebSockets, queues, extra machines).

## 4. Engine invariants (unchanged from v1 — keep them all passing)

1. Server-issued, high-entropy, opaque session cookie (HttpOnly, SameSite, Secure in production), validated against the database. Never accept a participant ID from the client as authority.
2. Two seats per table (Checker A, Checker B). Creating a table claims A and returns an unguessable invite URL; a second browser identity claims B by clicking **Join** (a GET never claims a seat). Same identity in two tabs is one member. A third identity cannot join. No seat replacement.
3. Writes are ordinary same-origin JSON POSTs with bounded bodies. Reads: GET snapshot + SSE stream. On every SSE (re)connection, authorise membership and send a fresh database-derived snapshot filtered for that identity; after every committed change, broadcast fresh filtered snapshots with a monotonically increasing table version. Clients never roll back to an older version. Lightweight keepalive; clean up closed streams.
4. **One allowlist serializer** builds every GET, POST response and SSE payload, so hidden data cannot leak through a second path. Private responses are `Cache-Control: no-store`.
5. Submissions are immutable once accepted. A duplicate identical POST is harmless; a changed repeat is rejected and cannot overwrite. Concurrent submissions create exactly two rows and one reveal.
6. Reveal happens only when both submissions for the round are durably stored.
7. Progression requests name where they come from (`fromRoundId` or `fromStage`). Concurrent identical requests advance exactly once; stale requests never skip or mutate history.
8. SQLite is the source of truth; persist before broadcast. Restarts and redeploys lose nothing accepted.
9. Do not log cookie tokens or full submitted answers.
10. Nothing secret (answer keys, accepted pairs, feedback, the bank file, fixtures, test files, the database) is served as a static asset or bundled into front-end code.

## 5. Teaching flow and table stages

Table `stage` values, in order: `waiting_for_partner` → `training` → `training_summary` → `transfer` → `completed`.

| Stage | Screen (ui-reference state) | What happens | Leaves the stage when |
|---|---|---|---|
| — | `start` | Home: three goals, how it works, time needed, Create table, My tables, links to Guide and Sources | — |
| waiting_for_partner | `waiting` | Invite link; prebrief from the facilitator (Lee); "Before you start" card | B joins → create round 1 |
| training | `checking` → `signed` → `debrief` | Rounds 1–6 (cases C1–C6 in bank order) | Next from round 6 → `training_summary` (no new round) |
| training_summary | `summary` | Personal + pair summary of rounds 1–6 | Either member clicks **Start the new situations** (`fromStage: "training_summary"`) → create round 7 |
| transfer | `transfer-intro` banner + `checking`/`signed`/`debrief` | Rounds 7–9 (T1–T3). Same independence and reveal rules | Next from round 9 → `completed` |
| completed | `end` | Training and transfer shown separately; earlier practice in this browser; print | — |

The prebrief and the "Before you start" card stay reachable from every later screen (toolbox).

If a partner leaves, keep the table; show that they can return in the same browser; offer a new table. A table that stops early is "in progress" and its summary says how many cases were completed.

## 6. Case bank

### 6.1 Loading and versioning
- Load `content/case-bank.v2.json` at start-up from a server-only path. Validate it (fail start-up with a clear message if invalid): five field keys; every case has an answer for each key; every accepted pair uses a known action and evidence id; no accepted pair uses `continue_checks` when any field is `mismatch`; every claim's `sourceIds` exist; every `medicineCardIds` entry exists; `reviewStatus` rules in §6.3 hold.
- Each table records `bankMajorVersion` and `bankVersion` at creation. Each round freezes a **complete snapshot** of its case (public part, answer key, accepted pairs, feedback, claims, card content, review status at the time). History never changes when the bank changes.
- v1 tables and rounds (if the repository has them) remain readable. Old submissions without `action`/`evidenceId` display "Not collected in this version" and are excluded from v2 summaries, not scored as wrong.

### 6.2 Public vs secret projection
- Public before reveal: setting, title (neutral, never names the error), simulation date-time, `secondCheckNote`, patient, chart (allergies, order, administration record), prepared, medicine cards, knowledge card, field/action/evidence option lists, case version and review status.
- Secret until both have signed: `answerKey`, `acceptedPairs`, `feedback`, `claims` mapping, any computed result, the partner's submission. Your own submission is returned to you after you sign, without any scoring.

### 6.3 Review status (content governance)
Values: `draft` (default) · `source_checked` (every claim checked against its listed source by the student) · `educator_reviewed` (a nursing educator or pharmacist actually reviewed it) · `withdrawn`.
- The agent never changes `reviewStatus`, `reviewerRole`, `reviewedAt` or `sourceCheckedAt`. Only the student does, in the JSON.
- `educator_reviewed` requires non-empty `reviewerRole` and `reviewedAt`; otherwise start-up validation fails.
- `source_checked` requires every claim to have at least one source whose `verification` does not start with "TO VERIFY".
- Badges (from the reference): draft → "Draft · not yet source checked"; source_checked → "Sources checked · not yet reviewed by a nursing educator or pharmacist"; educator_reviewed → "Reviewed by {reviewerRole}, {reviewedAt}"; withdrawn → not used for new tables; old snapshots show "This case version has been withdrawn" with the change note.
- If the student marks a version withdrawn or corrected, old rounds keep their snapshot and show a visible notice linking to the change note. Never silently re-score.

## 7. Answers

### 7.1 Submission body
```json
{ "fields": { "patient": "match|mismatch", "medicine": "...", "dose": "...", "route": "...", "time": "..." },
  "action": "continue_checks|reprepare|pause_clarify",
  "evidenceId": "all_fields_match|total_amount|identifiers|admin_record|allergy_record|route_form|patient_words" }
```
- All five fields required, initially unselected in the UI. Exactly one action and one evidence id from the bank's global lists (the same seven evidence options in every case, so the option list never hints at the answer).
- Reject missing, extra or unknown keys and values.
- **Consistency rule** (input validation, not correctness): if any field is `mismatch`, `action` must not be `continue_checks`. Error copy: "You marked a mismatch, so ‘Continue with the remaining checks’ doesn't fit. Choose another next step." All-match answers may choose any action — matching records can still need a pause.
- Validation errors never reveal the reference answer. Valid answers are accepted whether right or wrong.

### 7.2 Labels
Field, action and evidence labels and help text come from the bank; tables and the sealed-answer list use each option's `short` label. `continue_checks` must always show its help text: "Carry on with this scenario's remaining bedside checks. This is not permission to give a real medicine."

## 8. Results, debrief and summaries (pure functions)

Implement in one module with no I/O, unit-tested against `docs/content/scoring-fixtures.json`. The definitions in the fixture file's `rules` are normative.

### 8.1 Round result
For each seat: per field outcome TP/FN/FP/TN; decision `{accepted, actionOk, evidenceOk}`; `fullyCorrect` = all fields TP/TN and decision accepted.
For the pair: per mismatch field coverage `both | onlyA | onlyB | neither`; `sharedMisses`; `complementary`; `identical` (fields, action and evidence all equal); `identicalButNotReference`; `fieldAgreement` [same, 5]; `decisionCoverage` both/onlyA/onlyB/neither.

### 8.2 Debrief composer
`composeDebrief(snapshot, result, viewerSeat)` returns ordered blocks, using only bank text and templates (no generated wording):
1. **Result strip**: one headline chosen by the first rule that applies, using `templates.pair`: `identicalButNotReference` → `sharedMiss` (first shared-miss field) → `onlyOne` (first complementary field) → `decisionOnlyOne` → `decisionNeither` → `bothFullyCorrect` → `decisionSplit` → `identical`. Then chips: your decision fits / doesn't fit, agreement yes/no, "Mismatches on this tray: n · found between you: m of n" (or "No mismatches on this tray").
2. **Comparison table**: rows = five fields + "Next step" + "Evidence"; columns Checker A, You, Reference, Between you.
3. **Four blocks** from the case feedback: Finding, Evidence, Why it matters, Next step.
4. **Personal and pair lines** from `templates` (each template fires on its exact condition; `stoppedAfterOne` fires when a case has ≥2 mismatches and the viewer found ≥1 but not all).
5. Optional `realWorld` paragraph.
6. **Talk it through** (case `discussion`).
7. Sources for this case (claims → source titles with links), case version, review badge.
Materials show evidence highlights after reveal: elements tagged with `data-evidence` matching the case's accepted evidence ids get the `.ev` highlight.

### 8.3 Session summary (per seat, per phase)
Count only revealed rounds of that phase. Never average percentages; sum counts first.
- Mismatches: "You found {TP} of {TP+FN} mismatches" (+ per field).
- False marks: "You marked {FP} of {FP+TN} matching items as mismatches".
- Decisions: accepted pairs {n} of {rounds}; also action-only and evidence-only.
- Fully correct cases {n} of {rounds}.
- Pair: found between you {union} of {TP+FN}; shared misses; complementary finds; decision coverage both/onlyA/onlyB/neither with case links; field agreement {same} of {5×rounds} with the fixed note "Agreeing isn't the same as being right."
- Zero denominator → "No opportunity this time" (never 0%, 100%, NaN or undefined).
- Always show fractions; a simple CSS bar may accompany a fraction. No radar charts, no composite "safety score", no ranking.
- **Suggestions (max 3)**: each scoring item (5 fields + 1 decision per case) carries one capability tag (field items via `capabilityTags[].fieldKeys`; decision items via the case's `decisionTag`). For each tag, count distinct cases with ≥1 wrong item. ≥2 cases → `suggestions[tag].multi` with {k}; 1 case → `.one`; sort by distinct cases desc, then wrong items desc, then `capabilityTagOrder`. No wrong items → `suggestions.none`. Always append `suggestions.limited` as a caveat line. Each suggestion links to its cases' debriefs.
- Transfer phase uses the same functions; the UI words it as "In a new situation you applied it / still practising" per case; it never overwrites training results.
- An incomplete table shows "{n} of 6 cases completed" and is not a completed practice.

### 8.4 Earlier practice in this browser (descriptive only)
On the end screen and My tables: up to 3 previous **completed** tables of the current identity with the same `bankMajorVersion`, newest first, excluding the current table: date, table code, training mismatches found, false marks, decisions accepted, transfer decisions accepted, and "same case set as before (memory may help)" when `bankVersion` is equal. No cross-table suggestions or trend claims. Older bank versions are listed separately as "Earlier version". Only the owner of the cookie can see this; the partner never sees your history. Copy: "Practice records in this browser. They don't identify you or follow you across devices."

## 9. API (adapt names to the repo if they already exist; keep semantics)

- `GET /api/me/tables` — my tables (stage, progress, bank version).
- `GET /api/me/history` — §8.4 data for the current identity only.
- `POST /api/tables` — create, claim A.
- `POST /api/tables/:id/join` — claim B or resume membership.
- `GET /api/tables/:id` — filtered snapshot (stage, current round public view, my submission status, partner status Submitted/Not submitted, revealed rounds with results and debriefs, summaries when stage ≥ training_summary, end data when completed).
- `GET /api/tables/:id/events` — authorised SSE snapshots.
- `POST /api/tables/:id/rounds/:roundId/submissions` — §7.
- `POST /api/tables/:id/next` — body `{ "fromRoundId": "…" }` or `{ "fromStage": "training_summary" }`.
- `POST /api/tables/:id/log` — usage event `{ "type": "reference_opened", "ref": "<medicineCardId>|knowledge:<sectionHeading>" }`; allowlisted types and refs; server adds seat, round id and time; silently ignore more than 60 events per member per minute. Not used for scoring.
- Pages (server-rendered HTML, readable without JavaScript): `/`, `/t/:id`, `/readme/` (full README.md with headings), `/guide/` (teacher guide), `/sources/` (scope, review legend, grouped sources from the bank).
- `pnpm export:evaluation` — writes `docs/validation/data/export-<date>.csv` (table code, seat, phase, case id, case version, five fields, action, evidence, submitted-at minus round-created-at in seconds, reference_opened counts). No tokens, no cookie values, no IPs.
- `pnpm content:review-pack` — regenerates `docs/content/review-pack.md` from the bank.

## 12. Automated tests (spec/) — acceptance IDs

Use node:test (or the starter's runner), real HTTP against an isolated temporary database, and close servers and SSE streams reliably.

- **T01 Independence**: before both sign, no GET, POST response (including the first submitter's), SSE payload, initial HTML or static asset contains the partner's fields/action/evidence, `answerKey`, `acceptedPairs`, `feedback`, results or debrief blocks. Medicine cards and the knowledge card may be public.
- **T02 Static secrecy**: the bank file, fixtures, tests and database are not reachable over HTTP; no front-end bundle contains an answer key.
- **T03 Membership**: non-members cannot read snapshots, SSE, history or debriefs, nor submit, advance or log; forged ids in bodies are ignored; another cookie cannot read my `/api/me/history`.
- **T04 Validation**: missing/extra/unknown keys, unknown evidence id and the consistency rule are rejected without revealing answers; valid wrong answers are accepted.
- **T05 Immutability and concurrency**: identical duplicate harmless; changed repeat rejected; concurrent submissions → two rows, one reveal, same result for both; concurrent `next` from the same round or stage advances once; stale requests cannot mutate history.
- **T06 Round results**: every example in `scoring-fixtures.json → examples` reproduces exactly.
- **T07 Session summaries**: `mockSession` training and transfer summaries reproduce exactly for both seats, including suggestions order and kinds, decision coverage and fractions.
- **T08 Zero denominators and incomplete tables**: no mismatch of a field → "No opportunity this time"; the `incompleteExample` reproduces and the table is not listed as completed.
- **T09 Stages**: full flow waiting → training (6) → training_summary → transfer (3) → completed over real HTTP with two cookies; transfer results never alter training results.
- **T10 Snapshots and versions**: changing a case in a copy of the bank after a round was played does not change that round's content, answer or debrief; a withdrawn version shows its notice on old rounds; v1 rows (if any) remain readable and are excluded from v2 summaries.
- **T11 Review status**: draft never shows a reviewed badge; `educator_reviewed` without role/date fails validation; `source_checked` with a "TO VERIFY" source fails validation.
- **T12 Bank validation**: an accepted pair with `continue_checks` on a case with a mismatch, an unknown source id or an unknown card id fails start-up validation.
- **T13 Persistence**: restart the real app process on the same database file with the same cookies: an in-progress table resumes at the right stage and completed summaries are unchanged.
- **T14 SSE**: reconnect after a missed update returns the latest authorised snapshot; no hidden fields in any SSE message.
- **T15 Pages**: `/`, `/readme/`, `/guide/`, `/sources/` return server-rendered HTML with their headings before JavaScript runs.
- **T16 Logging and export**: unknown log types/refs rejected; stored rows contain no token; export CSV contains no token or cookie value.
- **T17 No AI calls**: no outbound network calls are made while scoring or summarising (stub the network in tests and assert it is untouched).

Keep the existing v1 tests unless they test behaviour this brief removes; replace those with the v2 equivalent and record the change in `docs/evidence-log.md`.

## 15. Known content gaps (owned by the student)

Every case and card is `draft`. Items marked ⚠ in `docs/content/review-pack.md` and sources marked "TO VERIFY" must be checked by the student before any status change. Implementation proceeds with draft content, clearly badged; it does not wait for review.
