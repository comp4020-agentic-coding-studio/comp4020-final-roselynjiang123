# 第二双眼睛｜Second Pair of Eyes
## 项目基准方案 v1.0

用途：作为我们后续讨论、范围判断、交互设计、开发和验收的共同基准。配套的 `Second_Pair_Sonnet5_Build_Brief_EN.md` 是开发执行版；两份文件表达同一个 MVP。本方案是规划材料，不是提交用 README 或 PROCESS。

## 1. 最终决定

做一个双人在线护理教学小游戏：两名参与者分别核对同一份虚构医嘱和待给药记录，独立提交五项比较结果；双方提交后，一起看到两人的判断、材料中的实际差异和解释。

核心问题：**多一个核对人，是否就多了一次真正独立的判断？两个人达成一致，是否就意味着判断正确？**

作品的价值来自可体验的规则，不依赖插画、复杂动画或大题库。最低可交付版本只有六个预设案例、一个双人核对桌、一套提交与揭晓流程、持久化记录和必要的测试。

“Good”的工作定义：好的教学核对系统应保护参与者独立形成判断的机会，让分歧和共同遗漏可见，并准确说明自己能保证什么、不能证明什么。

## 2. 定位与教育意义

面向护理学生及没有医学知识的课程访客。背景是用药核对，但任务是比较页面明确提供的信息，不要求参与者自行判断药物适应证、治疗剂量或临床处置。

预期学习目标：

1. 能按 patient、medicine、dose、route、scheduled time 五个维度比较材料。
2. 能说明独立核对为何需要在提交前避免看到同伴结论。
3. 能区分“意见一致”“材料匹配”和“临床安全”。
4. 知道重复核对不能替代其他安全措施，也不能据游戏表现推断真实临床能力。

这五项是本游戏选择的教学框架，不声称它们穷尽全部给药责任。所有药品均明确标为训练占位名称；剂量是无临床意义的训练单位。患者只使用合成编号。

页面简短提示：**Educational simulation. All records are fictional. Compare the supplied records; do not use this game to make clinical decisions.**

这不是临床认证考试，也不是研究独立核对效果的真实实验。完成游戏不等于已达到护理操作能力。

## 3. 文献立场与设计来源

### R1：独立性需要流程支持

ISMP Canada 对 independent double check 的定义强调，不应提前告诉另一位核对人预期看到什么，以减少对判断的影响。设计对应：在两人均提交前，服务端不向任何一方返回同伴的选择或标准答案。[R1]

### R2：独立核对要有选择地使用

ISMP 的实践文章支持有选择、正确地使用独立核对，同时指出过度使用和流程问题。设计对应：不宣传“检查越多越安全”，不制作“所有给药都必须如此”的临床规则。[R2]

### R3：效果证据存在限制

Koyama 等人的系统综述指出，现有研究不足以确立双重核对相较单人核对降低给药错误或伤害的效果，且独立性的定义与执行存在问题。设计对应：作品展示流程和判断，不声称证明临床效果，也不将游客数据包装为研究结论。[R3]

### R4：小范围、低干扰的共同体验

Amber Case 的 Calm Technology 原则强调减少注意力负担及使用解决问题所需的最少技术。设计对应：一个核对桌、安静的提交状态、无倒计时、无排行榜、无刷屏通知。这是借用部分设计原则，不声称整个教学游戏属于严格的 calm technology 产品。[R4]

目前不必再叠加 Reason 或锚定效应等理论。以上资料已能形成“独立性的实践主张—效果证据的限制—界面取舍”的论证。后续 README 应由作者阅读后亲自形成论点，不把本节直接当成最终论文。

## 4. 一次完整体验

### 进入与配对

1. 访客从 `/readme/` 了解作品，再进入 `/`。
2. 系统自动分配匿名浏览器身份；显示名为 Checker A / Checker B，不要求输入昵称。
3. A 创建核对桌并得到邀请链接。B 在另一个独立浏览器打开链接，点击 Join。
4. 每桌固定两席；第三个身份无法加入。一个浏览器的两个标签页属于同一身份，不能占两个席位。
5. 两人加入后开始；A、B 都可以先提交，没有固定的“第一核对人”。

### 核对

页面并排展示 Order（医嘱）和 Prepared record（待给药记录）。窄屏上下排列。

五个字段各有一组选项：Matches / Does not match；所有字段都要选，默认不选。另有一个最终判断：Records match / Discrepancy found。最终判断必须与自己五项选择一致，否则服务端拒绝提交。

这些按钮描述记录是否一致，不使用“安全给药”或实际“放行”。病例标题和编号不能提前提示错误类型。

提交前可修改本地选择；提交成功后本轮答案不可改。另一人只能看到 Submitted / Not submitted，不会看到选择、正确率、提示或局部反馈。提交状态只表示动作完成，不表示答案正确。

### 揭晓与教学反馈

双方提交后，系统同时允许两人查看：

- 两人的五项比较和最终判断；
- 两人的结论是否完全一致；
- 每个字段实际是否匹配，以及完整答案是否正确；
- 与材料直接对应的解释。

反馈必须区分：两人都正确；一人正确；两人都不完整正确（其中可能一致，也可能不一致）。共同判断错误时明确写“Agreement is not the same as accuracy”，但绝不强行制造错误或伪造同伴。

意见有分歧也直接进入教学揭晓，不进入讨论后重新提交。已经看到对方答案后，重交不能再称为独立核对；原始判断应保留。页面不实际执行任何药品放行。

### 后续回合与结束

揭晓页保留到有人点击 Next case。任一成员可推进，但请求必须带上当前 round ID；两人同时点击只推进一轮。对方自动看到新的当前回合。

六个案例按下表固定顺序出现，界面只写 Case 1–6，不用错误名作标题。固定顺序是减少实现成本的取舍；重复游玩会产生学习效应，因此记录不能用于比较干预效果。

完成六例后显示回顾：已完成案例数、每人的完整正确案例数（例如 4/6）和共同遗漏的案例。没有排行榜、奖励速度的评分或跨用户排行榜。

每一轮都即时保存，不需要完成六例才保存。My tables 入口列出当前身份参与的核对桌；同一浏览器保留 cookie 时，可在次日返回继续或看历史。

## 5. 最小题库：六个案例

每例都展示完整的五项材料。不需要用户了解真实药物，不进行剂量换算。每例的正确答案从字段比较确定。

统一基础医嘱：Patient = SIM-014；Medicine = Training Medicine A；Dose = 0.5 training units；Route = Oral (by mouth)；Scheduled time = 09:00。

| 案例 | 待给药记录相对于基础医嘱的变化 | 正确判断 | 揭晓后的教学重点 |
|---|---|---|---|
| 1 | 无变化 | 五项匹配 | 核对不等于总要找出一个错误 |
| 2 | Patient 改为 SIM-041 | patient 不匹配，其余匹配 | 不能只凭编号看起来相似就确认 |
| 3 | Medicine 改为 Training Medicine B | medicine 不匹配，其余匹配 | 按完整名称比较，不依赖熟悉感 |
| 4 | Dose 改为 5 training units | dose 不匹配，其余匹配 | 小数点变化带来十倍差异；仅为训练数据 |
| 5 | Route 改为 Intravenous (into a vein) | route 不匹配，其余匹配 | 比较给定途径，不判断占位药物的临床适用途径 |
| 6 | Scheduled time 改为 21:00 | scheduled time 不匹配，其余匹配 | 比较记录的计划时间，不模拟临床允许的给药时间窗 |

常驻简短词汇说明解释五个字段和两种途径。材料没有倒计时，不与设备时钟关联。出题规则、正确答案和解释是自编教学内容，不是从文献复制的经验证量表。

## 6. 最小画面与界面规则

四类视图足够：介绍/创建桌；等待同伴；核对与揭晓；回顾/历史。可由同一桌页面按状态切换，另保留 `/readme/`。

使用系统字体、浅色背景、深色正文、单一强调色、清楚表格和状态标签。不画医院、人物或药车；不使用图片生成、画布、拖拽、音效或装饰动画。

使用原生按钮与 radio、明确 label、可见键盘焦点。不能只靠红绿颜色表达对错。更新状态不抢走键盘焦点、不清空未提交选择；刷新后未提交草稿可以丢失，但已确认保存的答案必须恢复。

共同在场感来自同伴加入、提交及一起揭晓，不额外承诺精确的在线/离线状态，以避免引入 presence 和心跳超时管理。

## 7. 技术基线

默认采用 Node.js + Express + better-sqlite3 + 原生 HTML/CSS/JS，使用课程 pnpm 工作流。选择与 starter 和依赖相容的受支持 Node LTS 并锁定版本，不追求最新版本。不引入前端框架、ORM、WebSocket、Redis 或外部 AI API。

采用 **普通 POST 写入 + SSE 状态推送**。每次建立或重建 SSE 连接，服务端从 SQLite 发送按当前身份过滤的完整快照；数据库提交成功后才推送更新。这样不需要保存可重放的事件队列。EventSource 自动重连不等于自动恢复业务状态，应用仍必须重新读库。[T1]

选择 SSE 是因为提交动作离散、只需服务器把状态变化送到浏览器。正常连接下以约一秒内可见为目标，必须在部署环境实测，不能只凭 API 名称宣称达标。

只运行课程允许的一台机器和一个持久 volume。生产数据库放在 volume 实际挂载目录，由环境变量配置；本地和测试使用不同路径。不能放在临时根文件系统，不能在启动时清空或重建已有数据。[T2]

数据库最少保存：匿名会话；核对桌与两个成员；回合与材料/答案/解释的版本快照；不可变提交。为 (round, participant) 建唯一约束。成员加入、最终提交和推进回合用事务处理。每轮保存题目快照，避免日后题库修改改变旧成绩。

身份由服务器创建的高熵随机 token cookie 识别，cookie 对应关系保存在数据库；cookie 设 HttpOnly、SameSite、生产 Secure。客户端不能自行指定 participant ID。刷新与重启保留身份；清除 cookie 后无法恢复原身份是 MVP 已知限制。

邀请链接只允许领取第二席，不允许旁观者读取他人提交。两个席位都有人后，新身份不能替换离开的成员；可新建桌。这里区分的是浏览器身份，不验证两个真人，更不保证两个人没有线下交流。

## 8. “Good”到规则与验证的映射

| 主张 | 实现规则 | 检查或判断 |
|---|---|---|
| 支持独立判断 | 双方提交前不泄露同伴答案及答案键 | 检查 GET、POST 响应、SSE、HTML 和静态资源；提交单据也不得泄露个人正确率 |
| 身份有意义 | 同一身份不能占两席或提交两份 | 同身份多标签、第三人加入、越权提交检查 |
| 分歧不会消失 | 原始答案不可修改，揭晓逐项展示 | 不一致、双方共同出错、全部正确等测试 |
| 不把共识当正确 | agreement 与 accuracy 分开计算 | 两人同样答错的固定测试；不产生真实给药授权 |
| 共享结果可信 | 事务、唯一约束、提交后推送 | 并发 join/submit/next，重复请求，旧回合请求 |
| 记录可回访 | 所有已接受动作入库，历史保留 | 同 cookie 重启进程、重新部署后检查；未完成桌也能继续 |
| 不制造速度压力 | 无倒计时、速度分、排行榜 | 界面审阅和试玩 |
| 非专业访客也能理解 | 词汇说明、只比较页面材料 | 两名同学只凭 URL 试玩，记录卡点与改动 |

不能机械证明的部分：用户是否理解独立性、是否感到被催促、反馈是否具有教育意义。以少量真实试玩、问题和观察支持判断；未做验证前只能写设计意图，不能声称已经提高学习效果。

## 9. 明确不做

- 非独立对照模式、A/B 实验、检出率比较或统计显著性。
- 聊天、昵称输入、注册登录、排行榜、角色扮演医院地图。
- 真实患者资料、真实处方上传、真实药物推荐、自动生成病例。
- 讨论后覆盖首次答案、实际放行药品、医学资格认证。
- 多机部署、微服务、复杂权限层级、自动接管失联席位。

这些都是范围决定，不是待开发功能。今后增加功能，必须说明它如何支持核心论点，并同步修改这两份方案和验收标准。

## 10. 开发工作流和课程交付

1. 先读真实 starter 的 AGENTS.md（如有）、fly.toml、Dockerfile、spec/README.md、package.json、文档模板。保留现成检查与证据机制，确认两个 marking viewports。
2. 先部署 placeholder，验证 `/` 和 `/readme/`。若当前没有 token 或部署能力，完成可验证的本地准备并明确剩余阻塞，不声称已经上线。
3. 实现一题的完整双人路径：身份、配对、数据库、提交与揭晓；每步可验证。
4. 加 SSE、重连恢复、并发约束、历史回访及核心集成测试。
5. 扩展为六题、加反馈与回顾、完成简单排版和键盘使用检查。
6. 运行课程检查，部署并实测两浏览器同步、重启、重新部署与历史保留。记录真实结果。

提交应随实际工作形成，不人为限定每阶段只有一个 commit，也不补造过去的 crit。重要 agent 错误修复后，按问题性质加入规则或回归测试；不把每个小 bug 都变成冗长 CLAUDE 规则。

COMP4020 交付：线上 Fly URL、源码、400–600 词 README、900–1100 词 PROCESS、CLAUDE、spec、课程要求的 crit reflections 和提交记录。README 全文须在 `/readme/` 服务端 HTML 中可读；`pnpm check` 与 `pnpm check:evidence` 均通过。COMP4020 不需要 research-note.md。

作者亲自起草 README 和 PROCESS 的论点与反思；agent 可以提供来源、检查缺口和记录客观验证，但不能捏造动机、试玩、crit、文献阅读或实验结果。本方案不是代交这些文件。

## 11. 最终验收底线

- 两个独立 Chrome profile 能从 URL 完成创建、加入、独立核对、自动揭晓和后续案例。
- 同伴加入、提交、揭晓与推进在正常网络下约一秒内出现，无需刷新；实测留证。
- 揭晓前，不能通过页面、接口、SSE 或打包资源直接获得对方选择或答案键。
- 两人同意但答错时，反馈明确区分共识与准确性。
- 刷新、进程重启、重新部署不丢失已接受提交、身份关联和历史材料。
- 无同伴时说明等待并可分享链接，不伪造真人或用 AI 自动补位。
- 题目、来源、规则、测试与 README 主张一致，且不宣称临床有效性。
